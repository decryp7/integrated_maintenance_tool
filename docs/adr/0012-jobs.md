# 12. Jobs and notifications

- Status: accepted
- Date: 2026-10-18

## Context

Long work in Debrief had grown several shapes. Imports had their own progress and Cancel; streamed queries and
the folder survey had per-window id registries; downloads, storage clean-up and live tail registered with
the background-task registry (tray and status bar); AI requests were plain awaited commands, so a second
"Explain" while the model answered a chat ran at the same time on the one model in memory, and closing a
dialog lost the answer. Nothing told the user that a ten-minute export had finished while they looked at
another window, and nothing collected what happened while they were away (a live alert, files that were
not imported, a plugin switched off after crashes).

The user asked for one jobs system for every long-running task, with limits per kind enforced in Rust, a
pane, toasts and OS notifications, and a notification centre for what needs attention.

## Decision

1. **A jobs service in the shell** (`app/src-tauri/src/jobs`), evolved from the background-task registry:
   work that ends is a job; what runs until stopped (live tail, the process monitor, PerfMon) stays a
   background task. Running jobs are mirrored into the background tasks, so the tray and the status bar list
   and stop them as before.
   - **Pure core** (`queue.rs`, `model.rs`): one FIFO queue per kind with its limit (AI 1, research 1,
     analysis cores − 1, import 1 per window, export 2, download 2, collection 1, maintenance 1), at most 20
     waiting per kind (more are refused with a message), queued AI jobs can move up and down, a kind can be
     paused (the AI while its worker is quarantined). The state machine (`queued → running → done | failed |
     cancelled | interrupted`) is an enum whose only transition function refuses illegal moves. Time is an
     argument, so the visibility rules are tested with a fake clock.
   - **Service** (`service.rs`, Tauri-free): runs each job on its own thread when its kind has a slot, with
     a cancel flag, an optional stop action and progress probe, a ticker that samples progress and coalesces
     change events (never more than every 400 ms), Retry from the request saved with the job, and listeners.
     A panic in a job fails that job with the reason; the next one starts.
   - **Glue** (`mod.rs`): work the user starts and may leave (AI use cases, exports, the folder survey,
     applying a profile, storage clean-up) is queued with `jobs::spawn` and its command returns the job id at
     once (`ai_start`, `export_report`, `save_profile`...). `jobs_wait` lets the dialog that started it
     follow it while it is open (its state, progress and whole result); `jobs_unwait` when it closes. A job
     someone waits for posts no message (the dialog shows the outcome); otherwise the message's View opens the
     result. `jobs::run` remains for work a command must finish before it answers (opening files, a bundle's
     unpacking, streamed queries).
2. **Visibility.** A job shows after about 2 s (`VISIBLE_AFTER_MS`); quick work never flickers in and quick
   jobs are not kept. A job that ran about 10 s or more (`ATTENTION_AFTER_MS`), every failure the user cares
   about, and every research answer ask for attention: a message in the notification centre, its toast, and an
   OS notification through `notify.rs` (its setting and rate limit) when no Debrief window has the focus.
3. **AI requests are jobs.** Every use case (explain, summarise, root causes, the proposals, natural
   language to query, folder set-up "Improve with AI") starts with `ai_start` and returns its job at once:
   "Explaining event #7 — running in Jobs · Show in Jobs", then "Explanation ready · View" opens the answer
   (a failure has Retry). The proposal, query and regex dialogs may stay open showing the queue position,
   progress and Cancel, or be closed: "Review proposals" brings the proposal back. `ai_chat_send` returns the
   turn's job id at once and the answer streams as before once the job runs. While a turn waits, the chat shows "Queued
   (position n)". Cancel in the pane, the chat's Stop and the dialogs' Cancel reach the same flag; a turn
   cancelled while queued frees its chat and says so. A worker crash fails the running job with the reason;
   a quarantine pauses the AI queue (the waiting requests stay) and posts "AI requests are paused · Reset AI".
4. **The other long work** registers through the same helpers: imports (progress from the import's own
   counters, Cancel = the import's cancel), streamed queries and analyses (`jobs::analysis`, View opens the
   view with the query), exports and sharing (events, reports, bundles, diagnostics and the problem report
   through `jobs::start_file`: the dialog closes at once, the message says what was written and "Show in
   folder" reveals the file through the opener the snapshots folder uses, only the file the job wrote),
   applying a profile (checked and saved at once, the re-import is an import job with its progress in the
   status bar), a bundle's unpacking (an import job before its files open), model and runtime downloads, the
   folder survey (View reopens the wizard with its proposals), storage clean-up (Settings may be closed; View
   reopens Settings ▸ Storage with what was freed) and tool collections (a second collection while one runs is
   stopped with a reason).
5. **History is saved with the project** (UI state key `jobs`, `JobsRecord` v1, the last 100), like chats:
   the engine owns it, the UI keeps the last copy for synchronous saves. Jobs that were queued or running
   when Debrief closed or crashed come back as `interrupted`, with Retry when their request is known. A missing,
   damaged or newer record restores an empty history with a warning.
6. **A notification centre** (`app/src-tauri/src/notification_centre`; "Notifications" in the UI): what
   happened and may need attention. Messages have a source, a severity, a primary (and secondary) action the
   UI maps to the existing feature (View, Retry, Reset plugin, Set up format, Review proposals, Reset AI,
   Install update, Show), a link and a dedupe key: the same key merges into one message with a count
   ("Error spike on WEB02 (×4)"). Project-scoped messages go with the project (at most 200); app-scoped ones
   (update, crash recovery, the AI) live in `notifications.json` in the data folder (at most 100); read
   messages are trimmed first. Producers: finished and failed jobs, live alerts (mutes apply: muted alerts
   never reach it), files not imported, quarantined plugins, the paused AI, an available update, a recovered
   session or safe mode. Toasts preview new messages with the same action; clicking an OS notification
   focuses Debrief and opens the message (the click is recognised by the focus that follows it, because desktop
   notifications have no click callback).
7. **Research mode** (an amendment to ADR 0011): the AI may research the web by itself, read-only, as a
   `research` job. It searches with the user's engine in the visible browser and collects the result links
   once from that results page (ads and the engine's own links left out, redirect wrappers unwrapped), up to N
   (default 5, 1–10 in Settings ▸ Web browser, a request may ask for another number). It then opens each of
   them by its address, in order ("Reading result 2 of 5: example.org"), never by clicking on the page it is
   on: no further hops, no typing, no forms. A result that ends up on another site is skipped. It reads each
   page (redacted, capped, untrusted), asks the model what in it is relevant, and answers with a citation per
   page used and the pages it skipped (CAPTCHA, login, payment, nothing relevant, no answer in time). Nothing a
   page or the model says can choose an address: every address comes from the results page's links. The search text is checked by the leak guard; with
   workspace data in it the user confirms or edits it first. The model gets `web_research` in every chat
   unless "Let the AI research the web automatically" is off; then it only offers "Research this" and "Let
   the AI drive the browser" as buttons. Read-along and agent mode stay opt-in per chat.
8. **Wire contracts** are feature-local: `app/src/app/jobs/jobs.types.ts` and
   `app/src/app/notifications/notifications.types.ts`, mirrored by the Rust DTOs. The browser build has mocks
   of both (`mock-jobs.ts`, `mock-notifications.ts`) that the AI, share and live mocks run their slow work
   through.

## Consequences

- Starting an AI request, an export or a profile change never blocks the UI, and AI requests never compete
  for the model; closing a dialog no longer loses the answer (View opens it from the pane or the
  notification).
- Limits are enforced in one place, in Rust, for every window; the UI shows what the engine reports.
- Every job state change is a domain event in the activity log (kind, id, duration; never titles or file
  contents).
- Commands that start a job answer with its id, not with the work's value: what the work produced is the
  job's result (`jobs_wait`, `jobs_result`) and its message line. Checks that need no work (arguments, the
  file to replace) still fail the command at once, so dialogs can ask before anything is queued; what only
  the work can find out fails the job, with Retry.
- Desktop notifications have no click callback on every platform; "open the message on click" relies on
  the focus event that a click gives Debrief and is not guaranteed on all desktops.
